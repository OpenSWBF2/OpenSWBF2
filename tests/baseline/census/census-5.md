## Format audit (D-47)

C4477 checks only the CRT printf family, and census-5 has no C4477 site. `LOG` / `RedLog::Write`, `PblTraceP`, `RedWarning::LogMessage` and `RedWarning::DialogBoxMessage` were audited in two parts:

1. Arguments passed without a cast. A scratch worktree added `_Printf_format_string_` to the format parameter of those four declarations (and to the 43 `PblTraceP` redeclarations in `.cpp` files). Then it built every project for Release|x64 with `/analyze`. PREfast checks every call against its format string at x64 width. A planted control in the same setup (`PblTraceP("%08X", void*)`, `PblTraceP("%u", size_t)` and `LOG("%x %d", void*, size_t)`) gave C6273 and C6328 on x64, so the method catches pointer and `size_t` arguments. Result over all nine projects: no C6273, no C6328, no C6067. The only findings are 10 C6340 sign mismatches (`unsigned` passed to `%d`) at `LuaMemory.cpp:221`, `pcRedRenderer.cpp:4281`, `pcRedSegment.cpp:448` and `sndstreamcapturesource.cpp:346`. These are the same width on both platforms, so they are not width sites.
2. Arguments cast to an integer type before the call, which PREfast cannot see. Every call to those functions whose arguments hold a cast to `int`, `unsigned`, `long`, `DWORD` or similar was listed (21 calls) and each operand's type was read. 17 cast an `int`, `DWORD`, `HRESULT` or `unsigned` value and are the same on both platforms. ## Open items (no owner in 45-05 to 45-11)

- `tests\unit\float_corpus.cpp:945` `math corpus` and `:960` `math corpus x87 pc24`: 100 lines of `corpus\mathfn\math.txt` differ on x64 (sin, cos, tan, asin, acos; float and double). Cause: the CRT math routines called differ per architecture. The x86 tests object calls `__libm_sse2_{sin,cos,tan,asin,acos}_precise` for both the float and the double forms (the float forms go through the double routine). The x64 object calls the x64 UCRT exports `sin`, `sinf`, `cos`, `cosf`, `tan`, `tanf`, `asin`, `asinf`, `acos` and `acosf` (dumpbin of `float_corpus.obj` and of the tests exe imports). A scratch probe that calls the same CRT functions on the 100 inputs gave the corpus value for all 100 on x86 and the x64 T1 value on x64. The exception is `asin.f` and `acos.f`, where the probe went through the double routine and so matched the corpus. With `_set_FMA3_enable(0)` the x64 result moved back to the corpus value for 6 of the 100 (4 `cos.d`, 2 `tan.d`). The other 94 differ because the algorithms differ, not because of FMA3. This is not a pointer-width difference. No locked decision in 45-CONTEXT.md and no plan from 45-05 to 45-19 covers it. ROADMAP Phase 48 (PAR-01) owns "a math corpus ... passes on x64" and FMA3 off. That conflicts with the Phase 45 exit "the T1 suite green on both platforms" until the orchestrator decides.
- `tests\unit\layout_pins.cpp` is `#if defined(_M_IX86)` (328 static_asserts, x86 only). The x64 layout tables belong to Phase 49 (45-CONTEXT.md out of scope), so it has no owner from 45-05 to 45-11 and no `PIN` row.
